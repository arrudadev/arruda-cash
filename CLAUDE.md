# CLAUDE.md

Guidance for AI agents working in this repository.

## Stack

- **AdonisJS 7** (`@adonisjs/core`) — TypeScript-first Node.js framework, ESM (`"type": "module"`), Node ≥ 24.
- **Inertia.js + React 19** (`@adonisjs/inertia`, `@inertiajs/react`) — server-routed SPA, no SSR (disabled in `vite.config.ts`).
- **Lucid ORM** (`@adonisjs/lucid`) on **SQLite** (`better-sqlite3`) locally; see [Database](#database) for Turso.
- **Vite 7** for the frontend build, **pnpm** as the package manager.
- **Tuyau** (`@tuyau/core`) — generates a typed API client and a route registry consumed by the frontend and by `start/routes.ts`.
- **Biome** for linting/formatting (not ESLint/Prettier).
- **Tailwind CSS v4 + shadcn/ui** for styling.
- **Japa** for tests (unit / functional / browser suites).

Run everything with `pnpm`, not `npm`/`yarn` — `pnpm-lock.yaml` is the source of truth.

## The generated layer — read this before touching models, controllers, or routes

This app relies on **code generation** wired into `adonisrc.ts` (`hooks.init`):

```ts
indexEntities({ transformers: { enabled: true, withSharedProps: true } }),
indexPages({ framework: 'react' }),
generateRegistry(), // Tuyau
```

This produces `.adonisjs/` (server + client generated code) and `database/schema.ts`. **Never hand-edit `database/schema.ts` or anything under `.adonisjs/`** — both carry a `DO NOT EDIT` header and are regenerated automatically.

Concretely:

- Each Lucid migration for a table produces a generated `*Schema` class in `database/schema.ts` (e.g. `UserSchema`) with `@column()` declarations inferred from the migration's columns and types.
- Models **compose** the generated schema instead of declaring columns themselves:
  ```ts
  export default class User extends compose(UserSchema, withAuthFinder(hash)) {
    get initials() { /* only hand-written extras go here */ }
  }
  ```
  To add/change a column: edit the migration (and run it), not the model or `schema.ts`.
- `indexEntities({ withSharedProps: true })` also generates the `Data.SharedProps` type (from `@generated/data`) used to type Inertia page props (`children.props.flash`, `children.props.user`, etc. in `inertia/layouts/default.tsx`).
- Controllers are referenced through a **generated registry**, not direct imports, in `start/routes.ts`:
  ```ts
  import { controllers } from '#generated/controllers'
  router.get('login', [controllers.Session, 'create'])
  ```
  Route names (`session.create`, `session.store`, ...) are auto-derived from controller/method names and used as-is in the React layer via `<Link route="...">` / `<Form route="...">`.

**Workflow when you change a table:** edit the migration → `node ace migration:run` (or `migration:fresh` in dev) → `database/schema.ts` regenerates → update the model/validators/transformers to match, if needed.

**Adding a new controller or Inertia page:** the `controllers` registry (`#generated/controllers`) and the page-name union type used by `inertia.render()` are also generated by these same hooks — but only when the app boots **through the assembler** (`node ace serve`, `node ace build`, `node ace test`), not for one-off commands like `node ace list:routes`. After adding a new controller/page, run `node ace serve` (Ctrl+C once it logs "codegen: created N file(s)" / "Ready in") or `pnpm typecheck` will fail with "Property 'X' does not exist" / a page-name type error even though the code is correct.

**Typing `inertia.render('some/page', props)`:** the expected `props` shape is extracted from the page component's own prop type (`.adonisjs/server/pages.d.ts` does `ExtractProps<typeof PageComponent>`), not inferred from `inertia.render()` call sites. Keep a page's props type as one **flat object** (optional fields for anything that varies) rather than a discriminated union (`{ a: true } | { a: false; b: string }`) — the extractor collapses unions and drops the non-common fields, causing a false type error on the controller side even though the code is correct (see `inertia/pages/auth/accept_invite.tsx` / `app/controllers/invite_controller.ts` for the working pattern).

## Common ace commands

```sh
node ace make:controller <name>       # app/controllers
node ace make:model <Name> -m         # app/models + migration
node ace make:migration <name>
node ace make:validator <name>
node ace make:middleware <name>
node ace migration:run                # apply pending migrations, regenerates database/schema.ts
node ace migration:fresh               # drop + re-run all migrations (dev only)
node ace serve --hmr                  # dev server (also `pnpm dev`)
node ace test                         # run Japa suites (also `pnpm test`)
node ace repl
```

Prefer `node ace make:*` generators over hand-writing new controllers/models/migrations — they place files correctly per `adonisrc.ts` directory conventions and keep the generated registries in sync.

## Dev environment

Two ways to run it locally — same `.env`, pick one:

- **Native**: `node ace serve --hmr` (or `pnpm dev`), plus a Mailpit container for catching invite emails: `docker run -d --name mailpit -p 1025:1025 -p 8025:8025 axllent/mailpit`.
- **Docker Compose**: `docker compose up --build` boots the app (`Dockerfile.dev`, hot-reload via bind mount) and Mailpit together. The app service overrides a few `.env` values for the container network (`HOST=0.0.0.0`, `SMTP_HOST=mailpit`, `APP_URL=http://localhost:3333`) — don't change those in `.env` itself, that file stays correct for native runs. Run ace commands inside it with `docker compose exec app node ace <command>`. Mailpit data is not persisted (`docker compose down` clears it).

Either way, Mailpit's UI is at `localhost:8025`.

**`Makefile`** wraps the Docker Compose commands used day to day — run `make help` for the full list (`make up`, `make migrate`, `make invite EMAIL=... NAME="..."`, `make logs`, `make shell`, `make test`, `make lint`, `make typecheck`, `make down`, ...). All targets assume the stack is already up (`make up` first) and just `docker compose exec`/`docker compose ...` under the hood — nothing here replaces the native `pnpm` scripts, it's purely a shortcut layer for the Docker workflow.

## Auth

- Session-based auth only, `web` guard (`config/auth.ts`, `sessionGuard` + `sessionUserProvider` on `#models/user`).
- `User` model uses `withAuthFinder(hash)` — gives `User.verifyCredentials(email, password)` and password hashing on create.
- **There is no self-service signup.** Accounts are created only through the invite flow:
  1. An operator runs `node ace invite:create <email> [fullName]` to create an `Invite` (`app/models/invite.ts`, token stored as a SHA-256 hash, 72h expiry) and email a link to `/invite/accept?token=...`. Locally this goes through Mailpit (SMTP `localhost:1025`, web UI `localhost:8025`); in production it goes through Resend (`MAIL_MAILER=resend` + `RESEND_API_KEY`, see `config/mail.ts`).
  2. `InviteController` (`app/controllers/invite_controller.ts`) renders `auth/accept_invite` for a valid token; the invitee sets a password, the account is created (name/email copied from the invite) and logged in at that point. Invalid/expired/already-accepted tokens render the same page with `invalid: true` instead of raising — no separate error page.
  3. Uninvited visitors cannot register — do not reintroduce a public signup route/controller.
- Route/middleware groups in `start/routes.ts`: unauthenticated routes (login, invite accept) live under `middleware.guest()`; authenticated routes live under `middleware.auth()`. Follow this grouping for new routes.

## Database

- **Local development uses SQLite** (`better-sqlite3`, file at `tmp/db.sqlite3`) — this is the default `connection` in `config/database.ts` and requires no setup.
- **Turso** is supported for staging/production via the `turso` connection in `config/database.ts` (`client: 'libsql'`), driven entirely by env vars (`TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`). Switch by setting `DB_CONNECTION=turso` (and the two vars above) — do not change the code default away from `sqlite`.
- Primary keys are **UUID strings** (`selfAssignPrimaryKey = true` + a `@beforeCreate` hook generating the id), not auto-increment integers. Follow this pattern for new tables: `table.string('id').primary()` in the migration, matching self-assign + hook in the model.

## Styling

- Tailwind CSS v4 (`@import "tailwindcss"` in `inertia/css/app.css`, loaded via the `@tailwindcss/vite` plugin) + shadcn/ui components in `inertia/components/ui/`.
- Use the `cn()` helper from `~/lib/utils` to merge Tailwind classes conditionally.
- Add new shadcn components with `pnpm dlx shadcn@latest add <component>` rather than writing Radix wrappers by hand, unless the component doesn't exist in shadcn's registry.
- Don't reintroduce hand-rolled CSS files/selectors for new UI — use Tailwind utility classes and shadcn primitives.

## Linting & formatting

- **Biome**, not ESLint/Prettier. `pnpm lint` / `pnpm format` (see `biome.json`).
- Run `pnpm typecheck` (checks both the server `tsconfig.json` and `inertia/tsconfig.json`) before considering a change done.

## API responses

- `providers/api_provider.ts` attaches `ctx.serialize()` / `ctx.serialize.withoutWrapping()` to every `HttpContext`, wrapping payloads as `{ data }` (and handling Lucid pagination meta). Use this when adding JSON API endpoints instead of hand-rolling response shapes.

## Testing

- Japa suites: `tests/unit`, `tests/functional`, `tests/browser` (see `adonisrc.ts` → `tests.suites`).
- Run with `node ace test` (or `pnpm test`); a suite can be targeted with `node ace test <suite>`.

## Git

- Commit messages are **a single line, no body**. Don't add a `Summary`/bullet-point body even for large or multi-part changes — keep the subject line descriptive enough to stand alone instead.
